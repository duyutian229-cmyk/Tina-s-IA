## 〇、一句话结论

**技术上没有做不到的环节，整体可行；真正的问题不是可行性，而是"核心算法现在是一张查表"。**
加料不应加在功能数量上（付款、积分、会员都是纯 CRUD，IB 明确不给分），而应加在**算法与系统复杂度**上：把"单人查表选曲"升级为**多顾客并发仲裁 + 会学习的排序 + 队列感知的序列生成**。

### 1.2 三处最要命的含糊

1. **点单系统到底在不在范围内？**
   文档原话说必填输入是"已经在点单平台上的"（already on the order platform）——如果照文档写，她的作品就只剩"输入两个值 → 输出一首曲子"的推荐器，**范围小到撑不起 30 分的 IA**，而且失去了"咖啡馆应用"这个背景。但如果要做完整点单系统，纯 CRUD 部分又会吃掉大量时间。这个边界必须先划清。

2. **音乐播在谁的设备上？**
   "顾客自己的手机"和"店内扬声器"是两个完全不同的系统：
   - 播在**顾客手机**（私人、耳机）→ 各听各的，不存在冲突，算法只需"为这个人选一首"。
   - 播在**店内扬声器**（公共）→ 立刻产生"多人同时想要不同音乐"的仲裁问题，算法的深度直接上一个台阶。
   文档用 "and/or" 把这个问题绕过去了，但它决定了整个系统的技术天花板。

3. **多顾客并发完全没提。**
   文档的 7 条成功标准全都隐含"同一时刻只有一个顾客"。市区咖啡馆（新街口）的现实显然不是这样——这是文档与真实场景最大的脱节，也是**最大的一块加料空间**。

### 1.3 一个已经做对了的决定

文档把算法从"神经网络"退回到"透明确定性的打分法"，**这个退是对的**，理由见 §3.2。不要因为她口头提了 NN 就觉得要把它做回来。

| 2 | 服务端 | ✅ 可行 | 环境配置耗时 | Python + Flask 单文件/少文件；她用 Python 而非 Java（IB 两套都认，但她的技术栈描述是网页） |

| 9 | 时间预算 | ⚠️ 偏满 | 范围过大做不完 | 按 §4 砍范围 |

### 2.1 最容易被低估的技术风险：音乐播放（务必先做 30 分钟验证实验）

1. **浏览器自动播放策略**：现代浏览器（Chrome/Safari，尤其 iOS）**禁止无用户手势的自动播放音频**。如果播放是在"服务端推送通知 → 客户端自动播放"的路径上，手机上**一定放不出声**。
   → 必须在"提交订单"那一次用户点击里就创建/解锁 AudioContext，之后才允许服务端驱动播放。
   → **这是演示视频里最容易翻车的点**，建议 Tina 在做任何设计之前先写 20 行代码验证一次。

2. **局域网 http 下的浏览器权限**：`http://<局域网IP>` 不是安全上下文（secure context），只有 `localhost` 是。后果：
   - 定位（geolocation）**被禁用** → 不能靠定位自动取天气；
   - 部分音频/媒体 API 受限。
   → 这反过来印证：**天气必须是"可选输入"，并且能手动指定**。文档的成功标准 2 已经挡住了一半。
   → 如果要更干净，可以让服务端自己去取天气（服务端无此限制），前提是电脑能上网。

3. **版权**：曲库 30 段必须用 **CC0 / 免版税**素材（Pixabay、Free Music Archive、freesound 等）。
   → 这件事本身是宝贵的 **Criterion A / E 素材**：在问题情境里写清"为什么选 CC0"、在评价里写"如果商用会有什么法律约束"。

4. **无缝循环**：20 秒 loop 若在浏览器里用 `<audio loop>` 会有可闻的接缝。要无缝需要 Web Audio API（`AudioBufferSourceNode` + loop 点）——**工作量不小，且是她现有技能之外的**。
   → 决策：**要么接受轻微接缝（用 `<audio loop>`），要么把 loop 换成"完整短曲"**。不要为了无缝循环烧掉 10 小时。

5. **资源体积**：手机端加载，单曲文件应控制在 ~300KB 以内（ogg/mp3，低码率足够，背景音乐场景）。

### 2.2 LAN 演示的具体检查清单

- 家用路由器 + PC 跑服务端 + 手机连**同一个** WiFi；
- 手机访问 `http://<PC局域网IP>:<端口>`（不是 `localhost`）；
- **Windows 防火墙要放行该端口**（常见失败原因 1）；
- 路由器若开启 **AP 隔离 / 客户端隔离**，手机将无法访问 PC（常见失败原因 2）；
- 学校/咖啡馆网络可能禁止设备互访 → **演示必须自带路由器**，她的这个计划是对的；
- 提前演练一次"关掉外网"的完整流程，确认所有功能都能降级运行。

## 三、技术难度提升方向（按性价比排序）

### 3.0 判据：加料要加在算法上，不是加在功能上

`IA_Assessment_Guide_2027.md` 明确写：
> "选题复杂度要匹配 DP 深度；**纯模板 / 纯 CRUD / 拖拽工具产品无法得高分**。"

标准 D 占 **12 分**（总分 30），评的是"技术技巧与算法思维"。所以：
- ❌ 加付款、会员积分、优惠券、推送通知 → 纯 CRUD，**不加分**，只加工作量；
- ❌ 加手机原生 App → 工作量大、与算法思维无关；
- ✅ 加**推荐质量、并发仲裁、调度、学习反馈** → 直接落在 D 和 C 上。

### 3.1 方向一（强烈推荐）：从"单人推荐"升级为"多顾客并发仲裁"

**场景**：新街口咖啡馆同一时刻有 3–5 个顾客在店里，各自下单、各自想要不同的音乐。**谁的曲子放？放多久？下一个轮到谁？**

**为什么这是最好的加料点**：
- 20 秒 loop **天然就是一个时间片（time slice）** —— 调度算法会自然浮现，不是硬套上去的；
- 这是一个真正的"多用户共享资源"问题，复杂度匹配 DP 深度；
- **可测试性极强**：给定 3 个顾客同时下单，输出的播放序列是确定的，可以写测试用例；
- Criterion C 里能画出调度状态机；Criterion E 里能量化评价**公平性**（各顾客等待时长的方差、最大等待时长）。

**算法候选**（由浅入深，让她自己选）：
1. **FIFO 轮转**：按下单顺序轮流各放一段，最公平，实现最简单；
2. **加权优先级队列**：权重 = 等待时长 + 是否会员 + 订单复杂度（手冲比美式"值得"更长音乐）；
3. **时间片调度 + 老化（aging）**：防止某个顾客被无限饥饿——**"饥饿"这个词本身就是绝佳的 Criterion C 论证素材**。

**前置条件**：这条**只在音乐是"公共播放"时成立**。若音乐播在顾客各自耳机 → 无冲突 → 该方向不成立。**所以 §5 的第 1 个问题必须先答。**

### 3.2 方向二（强烈推荐）：把"确定性打分"升级为"会学习的排序"

这是回答她"如何训练"这个疑问的正解。

**两层的设计**：
```
第 1 层：可复现打分器（保留文档里已有的设计）
    score(track) = Σ weight[tag] × match(tag, 情境)
    → 满足成功标准 3（同一输入必定同一输出，可重复测试）★ 这一条不能丢

第 2 层：在线学习层（新增）
    顾客行为 → 反馈信号：听完 / 跳过 / 重播 / 手动换一首
    → 用简单在线算法更新 weight[]：
       · ε-greedy 或 UCB 多臂老虎机（推荐，理论支撑好、代码量小）
       · 或 perceptron / 单步梯度下降
```
**为什么这样解决了"没有训练数据"**：训练数据**来自真实使用**——每次顾客跳过或重播都是一条标注。不需要造假数据，也不需要预先离线训练。

**额外收获（这是最值钱的部分）**：Criterion E 可以做**对照实验**——
> 用固定权重的 baseline vs 学习后的权重，各跑 100 次模拟会话，比较**跳过率**。

这是 IB 标准 E 里最难得的**量化评价**（多数学生只能写"我觉得挺好"）。

**必须同时写清楚的两个点**（否则会被质疑）：
- **冷启动**：前 N 次使用默认权重，之后才进入学习；
- **探索率**：ε 设为多少、为什么（太保守学不到东西，太激进推荐质量差——**这就是 exploration/exploitation 权衡，是教科书级的论证素材**）。

### 3.3 方向三（推荐）：队列感知的序列生成

- 服务端维护**订单队列**，按饮品类型预估制作时长（手冲 4 分钟 / 美式 2 分钟 / 冷萃 1 分钟……）；
- **这一张"预估时长表"让她自己去咖啡馆实测**——这是极佳的 Criterion A 一手素材，也体现真实调研；
- 推荐的**曲目数量 = 预估等待时长 ÷ 20 秒**，给顾客一段**小播放列表**而不是一首。
- **好处**：把"选一首"变成"生成一个序列"——序列生成明显更像算法；而且天然接上方向一的调度问题。

### 3.4 方向四（中等）：多样性与去重约束

- 同一顾客连续下单不应永远得到同一首；相似订单也不应总是映射到同一首。
- 实现：简单的"最近 N 次推荐惩罚"，或 MMR（最大边际相关）。
- 代码量小、论证空间大，是推荐系统的真实工程问题。

### 3.5 方向五（中等）：店家侧分析面板

- 用文档已有的"会话日志"（成功标准 6）做 SQL 聚合：按时段 / 品类 / 天气统计**跳过率**，出图表。
- **好处**：让"店家为什么要用它"这个商业叙事闭环（文档开头讲的就是"不增加店员负担"）；SQL 深度足够（多表 JOIN + 聚合）。
- ⚠️ **风险**：容易做成纯 CRUD 报表。必须绑定到"**验证推荐算法是否有效**"上，它才是算法的一部分而不是报表。

### 3.6 方向六（小）：语录生成升级为模板 NLG

- 目前看起来是查表。可升级为：**槽位填充 + 语法规则 + 与所选曲目风格一致的用词库**，保证同一输入必定同一输出（保住可复现性）。
- ⚠️ **明确不要用 LLM API**：调用大模型不展示她自己的算法思维，反而会被认定为"核心逻辑不是自己写的"。

### 3.7 不推荐清单（要主动劝退）

| 不推荐 | 理由 |
|---|---|
| 真·神经网络训练 | 无真实训练数据；"用了 NN"本身不加分，加分的是算法思维与论证；讲不清训练过程反而扣印象分 |
| 在线支付 / 会员积分 / 优惠券 | 纯 CRUD，零算法含量 |
| 手机原生 App | 工作量大、与计算思维无关，且她已明确用网页 |
| 语音 / 图像识别点单 | 会喧宾夺主，把核心算法的篇幅挤掉 |
| 多语言 / 主题皮肤 | 零算法含量 |

## 四、建议的新范围（一页纸）

**核心叙事**：**"排队感知的咖啡馆个性化音乐点单系统"**

```
顾客侧网页（手机浏览器）
  看菜单 → 下单（品类 + 昵称 + 可选情境：天气/时段/氛围）
    → 返回一段「约 60–100 秒的个性化播放列表」+ 一句语录
    → 可跳过 / 重播（产生反馈信号）

店家侧网页（PC 浏览器）
  订单队列 + 当前播放 + 会话日志 + 一周统计

服务端（Python + Flask + SQLite）
  打分器（可复现） + 学习层（在线更新权重） + 调度器（多顾客仲裁）
```

**算法三件套**（对应 Criterion C 的三份算法文档）：
1. `score()` —— 可复现的打分与排序
2. `update_weights()` —— 从反馈中在线学习
3. `schedule()` —— 多顾客播放仲裁

**成功标准需要重写**：从现在的 7 条扩到约 9 条，新增的必须是**可验证**的，例如：
- 给定 N 个顾客的并发订单，系统输出的播放序列可在 2 秒内生成，且**任意顾客等待任意顾客的最长连续播放不超过 X 秒**（公平性，可量化）；
- 学习层开启后，模拟 100 次会话的跳过率**低于**固定权重 baseline（可对照，可复现）；
- 冷启动阶段（前 N 次）行为必须已定义且可测试。

> 另：现有文档成功标准第 4 条误写为 "Five."（应为 "5."），且第 6 条 "locally"（本地）与客户端-服务端架构矛盾——重写时一并处理。

## 六、方案修订（基于上述确认）

### 6.1 "店内扬声器"这个答案改变了三件事

**① 最大加料方向成立** —— 公共播放 = 多人同时在场 = §3.1 的并发仲裁是本作品的**技术主干**，不是可选项。

**② 两个原本标为"最易翻车"的风险直接消失**（这是意外收获）：

| 原风险 | 修订后 |
|---|---|
| 浏览器自动播放策略（手机上放不出声） | **消失**。音频由**服务端**播放（PC 接店内扬声器），不经过浏览器。服务端无自动播放限制 |
| 20 秒 loop 接缝（Web Audio API 工作量大） | **消失**。改用服务端播放库（`pygame.mixer`，`play(loops=-1)` 天然循环），比 `<audio loop>` 还干净 |

**③ 但新增两个风险**：
- **服务端音频播放**是她现有技能之外的一小块，需要 30 分钟踩点（`pygame.mixer` 支持 mp3/ogg；注意混音器初始化参数与文件格式匹配）；
- **录演示视频要捕获系统声音**（扬声器输出），录屏软件默认只录麦克风——这个必须在录视频之前测通，否则核心功能在视频里"看不见"。

### 6.2 顾客手机页面的定位必须重新设计（不能照文档写）

文档现在写的是"结果展示在顾客页 and/or 店内屏幕"。**既然音乐走店内扬声器，顾客手机就不放音频了**，那这个页面放什么？必须重新定义，否则顾客端的价值说不清。

**建议的新定位——"我的这一杯"页面**：
- 我的订单状态（已下单 / 制作中 / 可取）
- **正在播放的是谁选的、以及为什么**（"正在播放：为 3 号桌的雨天拿铁选的 《…》"）
- **我排在队列的第几位、还要等多久**
- **反馈按钮**：喜欢 / 换一首 / 重播 → 这既是有用的 UI，又是 §3.2 学习层的**唯一反馈入口**

这样设计之后，顾客页从"显示的余兴"变成**系统里真正有职责的一环**（实时状态同步 + 反馈采集），Criterion C 的 UI 设计部分立刻有内容可写。
→ 实时状态同步用**轮询（polling）**即可，不要上 WebSocket（多余复杂度）。

### 6.3 新增一个必须解决的算法约束：店内氛围一致性

公共播放暴露了一个真实问题：**如果一位顾客点了浓缩，系统给他放了死亡金属，整个咖啡馆的人都要跟着听。**

这不是 bug，是**公共场景的固有限制**，必须显式设计：
- **方案 A（简单）**：曲库预先限定在同一"店内风格"范围内，个性化只在风格内部做细分（如：明亮爵士 / 慵懒爵士 / 雨夜爵士）。**推荐这个**——工作量小，约束清晰，且让"曲库为什么是这 30 首"在 Criterion A 里有了硬理由。
- **方案 B（复杂）**：目标函数做成多目标加权——`总分 = α × 个人匹配度 − β × 与店内氛围的偏离度`，α/β 可调。
  → **这个 trade-off 本身是极好的 Criterion E 素材**：调 α/β 会怎样影响个人满意度与整体氛围？可以量化。

无论选哪个，**这条约束都要写进 Criterion A**——它证明了作者意识到"个性化推荐"和"公共空间"之间的张力，是**真实世界问题**的标志，比多加三个功能值钱得多。
